# 衡准 I10 全量人机交互逻辑推理验收账本 v1

> **历史证据边界**：本账本保留其生成时的场景推理和验收记录，不是当前实现或完整链路目标设计的最高权威。当前事实以实际代码、SQLite 状态和真实运行证据为准；完整链路目标以《衡准-I10-完整链路审计文档》为准。本文中的 v4、旧工具数和旧 Flowise 路径必须在重跑时按当前代码重新核对，不能直接覆盖当前事实。

## 1. 文档目的

本账本以其生成时的桌面导出包实现和当时可获得的运行证据为记录基线，逐条推演用户、Flowise Agent、Harness、Midscene、Playwright Builder 与用户后续决定之间的完整往返。重新验收时必须回到当前代码、SQLite 和真实运行证据，不得把历史账本直接当作当前运行证明。

本账本遵守以下记录规则：

1. 每完成一个独立等价类推理，立即写入一条编号记录。
2. 任何错误、超时、中断、失败关闭或人工阻塞都必须写入记录。
3. 每个中断同时记录：
   - 当前实现会怎样结束；
   - 缺少什么恢复入口；
   - 修复后应从哪个稳定状态继续；
   - 后续仍需走完哪些步骤。
4. 不因单个流程通过或失败停止，必须继续覆盖其他等价类。
5. “设计上存在”“后端有接口”“字段被保存”均不等于Flowise完整链路已经可用。
6. 模拟回答是基于当前节点模板、状态机和工具合同生成的等价用户可见表达，不声称逐字复现非确定性LLM措辞。

## 2. 完备性边界

自然语言本身有无限表述，无法逐句穷举。本账本以会改变系统控制流、状态、安全性或最终产物的输入等价类作为“所有可能情况”的有限边界。

### 2.1 输入维度

| 维度 | 等价类 |
|---|---|
| 主输入 | 自然语言、案例文件、视频、无主输入 |
| 补充图片 | 无图片、装饰图片、包含必要事实的图片、图片唯一承载案例、非法图片、低置信度图片 |
| 文本完整度 | 完整、缺URL、缺目标系统、缺步骤、步骤与预期不等长、歧义、空白 |
| 凭据 | 已就绪、未录入、过期、不存在、用户误贴明文 |
| 用户决定 | proceed、reject、未操作、自由文本误输入、重复点击、过期页面点击 |
| 作者化 | 成功、视觉模型失败、定位不一致、凭据解析失败、页面不可达、人工验证挑战 |
| 候选验证 | 四次全部通过、作者化失败、Playwright失败、稳定性部分失败、等待超时 |
| 脚本交付 | 下载成功、链接过期、Hash不一致 |
| 激活 | 激活、不激活、重复激活、版本冲突 |
| 执行 | 不执行、立即执行、单次定时、周期执行、时间歧义、非法时区、非法Cron |
| 正式运行 | 成功、产品缺陷、脚本失效、环境失败、人工验证阻塞 |
| 反向修复 | 不修复、候选生成失败、复验失败、激活修复、不激活修复、复跑、重新调度 |

### 2.2 状态结论

- `PASS`：当前实现证据足以支持该等价类走到预期终态。
- `CONDITIONAL_PASS`：仅在明确前置条件成立时可走通。
- `INTERRUPTED_RECOVERABLE`：当前流程中断，但存在可操作恢复路径。
- `INTERRUPTED_NO_ROUTE`：后端可能具备能力，但当前Agentflow没有继续路径。
- `FAIL_CLOSED`：系统按安全要求停止，未产生错误业务状态。
- `FAIL_OPEN_RISK`：系统可能继续但关键事实未被验证。
- `UNVERIFIED`：存在代码或合同，但缺少覆盖该范围的运行证据。

## 5. 分项推理记录

### R-001 完整自然语言、凭据已就绪、无补充图片

- 用户前置状态：当前Flowise会话已有有效`credentialRef`。
- 用户输入：“创建复兴银行门户登录回归案例。入口为`http://127.0.0.1:18082/portal/login`，登录后验证右上角姓名和头像，再进入个人资料页验证姓名一致。”
- Agent等价回答：展示规范化案例摘要、入口、动作、预期和断言；说明`proceed`批准冻结草案并进入作者化，`reject`返回同旅程修改。
- 实际系统路径：分类`CASE_AUTHORING/NATURAL_LANGUAGE` → LLM结构化 → 确定性URL、数组、凭据引用和多模态对象规范化 → `journey_prepare` → `CONFIRM_EXACT`。
- 用户下一次操作：点击`proceed`。
- Agent下一次行为：提交精确`proposalId/payloadHash/version`，进入`case_prepare`和作者化链路。
- 错误或中断：无必然中断；结果仍依赖被测门户和视觉模型可用。
- 当前结论：`CONDITIONAL_PASS`。
- 修复后继续路径：不需要流程修复；运行失败时转入相应作者化或环境失败记录。

### R-002 完整自然语言、凭据尚未录入

- 用户前置状态：没有有效`credentialRef`。
- 用户输入：与R-001相同的完整案例描述。
- Agent等价回答：“请先打开本机安全凭据页面录入账号密码；保存后返回对话发送‘继续’。不要在对话中输入秘密。”
- 实际系统路径：`journey_prepare`识别`credentialRef`缺口 → `credential_session_create` → 返回一次性本机录入链接。
- 用户下一次操作：在本机表单完成DPAPI加密保存，然后发送“继续”。
- Agent下一次回答：读取`credential_session_get`；有效时重新结构化原案例并显示唯一冻结草案。
- 错误或中断：用户只打开表单但未保存时，“继续”后仍缺凭据；系统不会进入作者化。
- 当前结论：`PASS`。
- 修复后继续路径：凭据录入失败时重新生成会话；成功后回到R-001的确认节点继续。

### R-003 自然语言缺少入口URL

- 用户前置状态：凭据有效。
- 用户输入：“验证复兴银行门户登录和个人资料姓名一致。”
- Agent等价回答：“案例尚不能提交，请补充入口地址。”
- 实际系统路径：LLM候选 → 确定性规范化产生`I10_ENTRY_URL_REQUIRED` → Harness旅程进入`NEEDS_INPUT`。
- 用户下一次输入：“入口是`http://127.0.0.1:18082/portal/login`。”
- Agent下一次回答：当前实现会将其作为新的普通用户消息再次分类和重建候选；如果会话状态正确保留原描述，可以重新形成冻结草案。
- 错误或中断：`journey_input_submit`当前不支持`INITIAL_CASE_INPUT`，因此缺口补充不是严格的同旅程输入提交；会话状态丢失时可能只得到一个缺上下文的新草案。
- 当前结论：`INTERRUPTED_RECOVERABLE`。
- 修复后继续路径：为`INITIAL_CASE_INPUT`增加同旅程提交与合并；修复后应从`NEEDS_INPUT`回到`READY_FOR_CASE_APPROVAL`，再继续R-001。

### R-004 用户在首次消息误贴账号、密码、验证码或PIN

- 用户前置状态：任意。
- 用户输入：“账号〈明文账号〉，密码〈明文密码〉，验证码〈一次性验证码〉，请执行登录案例。”
- Agent等价回答（安全目标）：应在任何LLM调用前提示改用本机安全凭据页面，并拒绝处理秘密。
- 实际系统路径：当前首节点先调用分类LLM，原始`question`会进入模型提示；后续`journey_input_submit`的秘密检测无法撤回已经发送给模型的内容。
- 用户下一次操作：更换已经暴露的测试密码，通过本机表单重新录入，只在对话中保留`credentialRef`语义。
- Agent下一次回答：重新建立不含秘密的新旅程。
- 错误或中断：属于`FAIL_OPEN_RISK`，因为安全拦截位置晚于首次LLM。
- 当前结论：`FAIL_OPEN_RISK`。
- 修复后继续路径：在Flowise入口与分类LLM之间增加确定性本地秘密扫描；命中后不调用LLM、不写旅程正文，只返回安全录入入口。用户完成重录后继续R-002。

### R-005 空白、寒暄或无法识别的首次输入

- 用户前置状态：无活跃旅程。
- 用户输入：空白、“你好”或与回归测试无关的内容。
- Agent等价回答：寒暄可进入`HELP`并说明支持的操作；空白或无法识别内容应要求描述案例，不应调用业务MCP。
- 实际系统路径：分类为`HELP`时可正常返回；分类为`UNSUPPORTED`时Harness返回可重新表述状态；真正空白值是否在调用分类LLM前被拦截没有独立入口证据。
- 用户下一次输入：按示例提供目标系统、入口、成功步骤和预期结果。
- Agent下一次回答：创建新的案例旅程。
- 错误或中断：空白首次输入仍可能消耗一次LLM请求，但不会合法进入案例批准。
- 当前结论：`CONDITIONAL_PASS`。
- 修复后继续路径：增加入口空白短路；修复后直接显示帮助简报，再进入R-001或R-002。

### R-006 完整自然语言＋装饰性图片

- 用户前置状态：凭据有效；图片不承载任何案例必要事实。
- 用户输入：完整文本案例并附产品Logo或无关截图。
- Agent等价回答：按自然语言生成冻结草案，不应把装饰图片误认为业务事实。
- 实际系统路径：`supportingImages`可进入Flow State，但当前Agentflow未调用`image_ingest_submit/get`；脚本由文本草案驱动。
- 用户下一次操作：点击`proceed`批准文本草案。
- Agent下一次回答：进入作者化并最终给出`.cjs`候选。
- 错误或中断：图片被忽略，但由于图片不承载必要事实，不改变预期脚本。
- 当前结论：`CONDITIONAL_PASS`。
- 修复后继续路径：补齐图片路由后，装饰图片应被标记为“无案例事实”，然后回到同一草案确认节点。

### R-007 完整自然语言＋图片包含额外但非必要事实

- 用户前置状态：文本本身足以生成案例；图片补充按钮名称、页面布局等辅助事实。
- 用户输入：完整文本并附登录页面截图。
- Agent等价回答（目标）：简报应区分“用户文本事实”和“图片候选事实”，只把经确认的图片事实写入`CaseDraft`。
- 实际系统路径：当前图片没有进入OCR、视觉分析或事实确认；草案可能由LLM根据文本自行补全，不能证明按钮名称来自图片。
- 用户下一次操作：若草案文本仍正确，可批准；若草案引用了图片独有内容，用户无法核验来源。
- Agent下一次回答：继续作者化。
- 错误或中断：属于证据溯源缺失；功能可能跑通，但图片能力主张不成立。
- 当前结论：`FAIL_OPEN_RISK`。
- 修复后继续路径：`image_ingest_submit` → Worker OCR/脱敏 → `image_ingest_get` → 用户确认事实 → 生成`supportingImageIngestId` → 合并草案 → 再继续R-001。

### R-008 简略自然语言＋图片承载必要输入值或步骤

- 用户前置状态：文本只说“按图完成转账/登录”，图片包含收款人、金额、按钮顺序或期望结果。
- 用户输入：“按截图执行这个成功案例。”并上传图片。
- Agent等价回答（目标）：先处理图片，列出从图中提取的非秘密事实，要求用户确认低置信度内容，再形成草案。
- 实际系统路径：图片处理节点缺失；分类和结构化LLM只拿到文本与图片元数据，无法可靠读取图像像素。
- 用户下一次输入：若Agent追问，应把必要的非秘密事实用文字补充；秘密仍通过本机凭据或运行时人工输入。
- Agent下一次回答：文本补齐后可重建草案。
- 错误或中断：不补文字时可能产生缺字段，也可能由LLM猜测并错误通过；两者都不等于图片链路成功。
- 当前结论：`FAIL_OPEN_RISK`。
- 修复后继续路径：接通图片OCR/视觉事实确认后，从`WAITING_USER`逐项确认，再把图片事实连同文本交给主控LLM；生成统一草案后继续R-001。

### R-009 仅上传图片，没有自然语言案例描述

- 用户前置状态：凭据可能有效或无效。
- 用户输入：只上传PNG/JPEG/WebP，不输入案例文字。
- Agent等价回答（目标）：识别为图片辅助的案例创建，要求补充目标或让用户确认从图片推断的案例目标。
- 实际系统路径：顶层`inputType`没有`IMAGE`；可能被分类为`NATURAL_LANGUAGE`但缺`naturalLanguage`，也可能错误进入文件导入，而案例文件导入不接受图片格式。
- 用户下一次输入：补充一句案例目标、入口地址和“图片用于补充步骤/输入值”。
- Agent下一次回答：理论上转为自然语言＋图片，但仍命中R-008的图片未编排缺口。
- 错误或中断：`INTERRUPTED_NO_ROUTE`。
- 当前结论：`INTERRUPTED_NO_ROUTE`。
- 修复后继续路径：明确允许“自然语言为空但图片存在”的`IMAGE_ASSISTED_CASE`入口，先建立图片任务，再要求最少目标确认，最后进入统一草案。

### R-010 非法、超限、伪造扩展名或路径越界图片

- 用户前置状态：图片能被Flowise上传，但内容可能不安全。
- 用户输入：超过20MiB单图、批次超过100MiB、扩展名与Magic不符、非PNG/JPEG/WebP或越过受控附件根目录。
- Agent等价回答（目标）：“图片未通过安全校验，没有进入OCR或模型；请重新上传受支持图片。”
- 实际系统路径：Harness图片接口具备格式、Magic、大小和受控路径失败关闭；但当前Flowise未调用该接口，因此不能证明入口会以该安全错误响应用户。
- 用户下一次操作：更换合规图片重新上传。
- Agent下一次回答：修复编排后应创建新图片任务；当前仍会落入R-006至R-009之一。
- 错误或中断：后端安全门存在，前端编排未覆盖。
- 当前结论：`UNVERIFIED`。
- 修复后继续路径：将图片入口绑定`image_ingest_submit`，把具体安全错误转换为用户简报；合规后继续R-011。

### R-011 图片OCR或视觉事实低置信度

- 用户前置状态：图片合规，但文字模糊、遮挡、语言混合或页面内容存在歧义。
- 用户输入：自然语言＋低清晰度截图。
- Agent等价回答（目标）：“已提取以下候选事实，其中若干项置信度不足。请逐项确认、修改或删除，然后点击proceed提交事实确认。”
- 实际系统路径：Worker、SQLite事实表和`requiresUserConfirmation`字段具备承载能力；当前Agentflow没有图片事实确认Human Input节点。
- 用户下一次输入：当前没有对应的结构化确认入口；用户只能重新用文字描述。
- Agent下一次回答：会重新走普通自然语言案例，而非完成图片事实确认。
- 错误或中断：`INTERRUPTED_NO_ROUTE`。
- 当前结论：`INTERRUPTED_NO_ROUTE`。
- 修复后继续路径：新增图片状态轮询和事实确认节点；确认后把`imageIngestId`、事实和溯源绑定到`CaseDraft`，再继续R-001。

### R-012 合规案例文件导入且草案完整

- 用户前置状态：有效凭据；上传XLSX、CSV、DOCX或JSON案例文件。
- 用户输入：“导入这个成功案例并生成自动化脚本。”附合规文件。
- Agent等价回答：文件处理中；完成后展示统一案例草案，`proceed`确认导入并进入作者化，`reject`进入修订。
- 实际系统路径：`CASE_FILE` → `ingest_submit` → `ingest_get` → `WAITING_USER` → Human Input确认。
- 用户下一次操作：点击`proceed`。
- Agent下一次行为：`ingest_decision_submit(CONFIRM)`，然后形成IntentPlan并进入作者化。
- 错误或中断：批量文件当前Flowise只把`items.0.draft`写入状态，多个案例的逐条选择和全量确认界面不充分。
- 当前结论：单案例`CONDITIONAL_PASS`；多案例`UNVERIFIED`。
- 修复后继续路径：批量文件应分页列出全部草案、错误和选择范围；确认后每个案例分别进入作者化账本。

### R-013 案例文件草案需要修改

- 用户前置状态：案例文件已解析为`WAITING_USER`草案。
- Agent等价回答：展示导入摘要并解释`proceed`确认、`reject`进入修改。
- 用户下一次操作：点击`reject`。

- 当前结论：A/B路径`PASS`；C为`UNVERIFIED`。
- 修复后继续路径：对URL查询执行秘密检测与显示脱敏；合法入口后回R-001。

### R-073 凭据会话过期、引用不存在或录入令牌无效

- 用户前置状态：凭据尚未READY或引用已损坏。
- 用户操作：打开过期链接、使用错误一次性令牌，或继续使用不存在的`credentialRef`。
- Agent等价回答：过期/无效时拒绝保存或拒绝作者化，并生成新的安全录入入口。
- 实际系统路径：Harness校验状态、过期时间、一次性令牌Hash、命名空间和凭据引用存在性。
- 用户下一次操作：使用最新完整链接重新录入。
- Agent下一次回答：新引用READY后重新显示案例草案。
- 错误或中断：旧引用不得静默回退到环境变量明文凭据。
- 当前结论：`FAIL_CLOSED`。
- 修复后继续路径：新会话完成后转R-002后半段。

### R-074 图片事实确认时批准、修订或拒绝

- 用户前置状态（目标修复后）：图片任务为`WAITING_USER`并有事实候选。
- 分支A：用户批准全部高置信度事实 → 写入`CONFIRMED`事实集。
- 分支B：用户修改部分事实 → 保存修订值与用户确认溯源，再次回读。
- 分支C：用户拒绝某事实 → 从CaseDraft输入中排除，但保留拒绝审计。
- 分支D：用户放弃全部图片 → 自然语言足够时继续纯文本；不足时保持缺口。
- 实际系统路径：Harness已有事实表和图片状态，但缺少公开图片决定工具与Agentflow确认节点。
- 错误或中断：当前四个分支均无法在Flowise完成。
- 当前结论：`INTERRUPTED_NO_ROUTE`。
- 修复后继续路径：新增`image_ingest_decision_submit`或等价受控MCP合同；确认后转R-069。

## 8. 连续链路组合验收剧本

### 8.1 本节解决的问题

前述R-001至R-074是控制流等价类，不是可直接照着操作的端到端剧本。本节把入口、中间门槛、作者化、脚本生成、用户决定和最终出口组合为连续旅程，供Codex按人类实际使用顺序操作。

“全部排列组合”采用有限状态路径覆盖，而不是把自然语言的无限措辞逐句枚举。只要两个输入触发完全相同的节点、状态转换、安全规则和产物，它们属于同一组合。每条剧本必须从一个入口开始，并到达以下任一稳定出口：

- `OUT-ACTIVATED_RUN_PASSED`：脚本已激活，立即执行通过。
- `OUT-ACTIVATED_SCHEDULED`：脚本已激活，单次或周期调度已创建。
- `OUT-CANDIDATE_RETAINED`：候选已验证但用户不挂载。
- `OUT-RESULT_DOWNLOADED`：结果或源码已通过短时链接下载并核对Hash。
- `OUT-REPAIR_RECOVERED`：正式回归失败后修复、复验、激活和复跑成功。
- `OUT-USER_ABORTED`：用户明确拒绝，系统保持原状态。
- `OUT-FAILED_CLOSED`：输入、模型、作者化或验证失败并安全停止。
- `OUT-WAITING_RESUMABLE`：等待凭据、人工验证、异步任务或用户补充，可凭权威ID继续。

### 8.2 Codex统一实操规则

每条`F-xxx`剧本都必须独立执行并保留以下证据，不得因为上一条成功而复用不可见状态：

1. 桌面导出包已经通过`VERIFY.cmd --no-pause`。
2. 使用新Flowise对话；只有标注“恢复旅程”的剧本可以复用`journeyId`。
3. 账号、密码、验证码、PIN和U盾口令只能在本机安全页面或被测银行页面录入，严禁进入Flowise消息。
4. 截图前遮盖密钥、令牌、凭据和URL敏感查询参数。
5. 每次MCP调用至少记录：工具名、安全参数类型、HTTP/MCP结果、返回的权威ID和版本；不记录秘密值。
6. 每次Human Input记录：页面摘要、点击`proceed`或`reject`、按钮本次语义、结果状态。
7. 每次异步等待记录：首次查询时间、最后查询时间、终态；不得用重复提交代替状态查询。
8. 每个脚本记录：`candidateId`、版本、SHA-256、纯Playwright结果、4个唯一稳定性运行ID、下载文件Hash。
9. 每个正式运行记录：`taskId`、脚本版本、终态、证据制品ID；每个调度记录`scheduleId`、时区和规范化时间/Cron。
10. 遇到本节已标记的当前缺口时，先记录真实失败，再按“修复后继续点”继续推演或在修复完成后从该点复测；禁止把目标回答冒充当前实际回答。

| 5 | 用户点击`reject` | 拒绝边 | “已取消本次修复；原脚本、事故和调度保持不变。” | 无repairProposalId；activeHash不变 |

通过条件：拒绝后没有静默修改候选、激活版本、任务或调度；失败记录仍可查询。

### 8.24 F-020：正式运行失败→修复候选→复验→激活→复跑→不调度

目标出口：`OUT-REPAIR_RECOVERED`。

| 步骤 | 人类或系统实际动作 | 预期节点/MCP | 模拟Agent可见回答与状态 | Codex验收证据 |
|---|---|---|---|---|
| 1 | 按F-019步骤1至3制造并分类正式失败 | `failure_get`→修复LLM | “已形成限域修复建议，等待用户决定是否验证候选。” | failureId |
| 2 | 用户在修复确认点击`proceed` | `repair_propose` | “只创建修复候选并重新执行完整验证，不会自动激活。” | repairProposalId |
| 3 | Builder规范化修复候选 | 确定性Builder | “正在进行纯Playwright和4次稳定性验证。” | 新candidateHash |
| 4 | 纯Playwright＋4次全部通过 | `candidate_get`/修复查询 | “修复候选已通过验证，等待激活确认。” | 4个新runId、证书 |
| 5 | 用户点击`proceed`激活修复 | `decision_submit` | “修复版本已激活，但尚未复跑。” | activeHash切换为修复Hash |
| 6 | 用户点击`proceed`批准复跑 | `run_submit`→`task_get` | “已创建一次纯Playwright复跑。” | 新taskId |
| 7 | 修复复跑通过 | `result_inbox_list` | “修复复跑已经结束。” | PASSED、artifactId |
| 8 | Agent询问是否为修复版输入新调度；用户点击`reject` | 修复调度拒绝边 | “本次没有创建新调度，旧调度也没有被静默迁移。” | 无新scheduleId |

失败继续：步骤4失败转修复验证失败出口，原正式脚本保持不变；重新修订后必须产生新Hash并重新跑完整4次，不能从步骤5继续。

### 8.25 F-021：周期回归失败→修复→复跑→创建新的周期调度

目标出口：`OUT-REPAIR_RECOVERED`和`OUT-ACTIVATED_SCHEDULED`。

| 步骤 | 人类或系统实际动作 | 预期节点/MCP | 模拟Agent可见回答与状态 | Codex验收证据 |
|---|---|---|---|---|
| 1 | 已激活脚本绑定一个周期调度 | `schedule_get` | 调度处于ACTIVE | oldScheduleId |
| 2 | 周期触发的正式运行失败 | Scheduler→formal runner | “周期任务失败，事故已记录。” | failedTaskId、oldScheduleId |
| 3 | 用户批准生成修复候选 | `failure_get`→`repair_propose` | “修复候选正在验证。” | repairProposalId |
| 4 | 修复候选通过纯Playwright和4次验证 | 修复候选链 | “修复候选已持证。” | 新Hash、4个runId |
| 5 | 用户点击`proceed`激活并再次点击`proceed`复跑 | `decision_submit`→`run_submit` | “修复版本已激活并创建复跑。” | activeHash、rerunTaskId |
| 6 | 复跑通过 | `task_get`→结果收件箱 | “修复复跑通过，请为修复版输入新调度或拒绝。” | PASSED |
| 7 | 用户输入“每个工作日09:00，Asia/Shanghai”，点击`proceed` | 修复调度解析 | Agent展示唯一规范化周期计划 | cron、timezone |
| 8 | 用户在二次确认点击`proceed` | `schedule_create`→`schedule_get` | “修复版周期调度已创建。” | newScheduleId绑定repairHash |
| 9 | Codex核对旧调度 | `schedule_get(oldScheduleId)` | 旧调度不得被静默修改；按策略应显式停用或继续保持其记录 | old/new调度关系 |

判失败条件：自动把旧调度的脚本Hash替换为修复Hash；跳过复跑直接建调度；新调度仍绑定旧脚本。

### 8.26 F-022：结果查询时尚未就绪→同任务继续查询→下载

目标出口：先`OUT-WAITING_RESUMABLE`，后`OUT-RESULT_DOWNLOADED`。

| 步骤 | 人类或系统实际动作 | 预期节点/MCP | 模拟Agent可见回答与状态 | Codex验收证据 |
|---|---|---|---|---|
| 1 | 用户在新对话发送“查询结果，任务参考编号为`<taskId>`” | 分类=`RESULT_QUERY`→`task_get` | “正在读取指定任务。” | taskId未被LLM改写 |
| 2 | 任务仍RUNNING或无artifactId | `任务是否已有结果文件` | “任务尚未形成可下载结果；稍后用同一编号查询，不要重复提交。” | 没有新run_submit |
| 3 | 等待任务终态后，用户再次发送同一查询 | `task_get` | “任务已形成结果，正在签发下载授权。” | 同一taskId、artifactId |
| 4 | Harness签发短时链接 | `artifact_download_grant` | “回归结果已就绪；请及时下载并核对Hash。” | grantId、过期时间、SHA |
| 5 | Codex下载并核对Hash | HTTP授权 | 完整报告和证据索引可打开 | `OUT-RESULT_DOWNLOADED` |

若用户不提供taskId：走`result_inbox_list`返回最近结果摘要，但不能猜测要下载哪一份；用户再选择明确taskId后从步骤1继续。

### 8.27 F-023：下载链接过期或Hash不一致→重新授权→安全下载

目标出口：`OUT-RESULT_DOWNLOADED`；Hash不一致期间保持`OUT-FAILED_CLOSED`。

| 步骤 | 人类或系统实际动作 | 预期节点/MCP | 模拟Agent可见回答与状态 | Codex验收证据 |
|---|---|---|---|---|
| 1 | 对已完成taskId查询结果并获得短时链接 | `artifact_download_grant` | Agent显示文件名和SHA | grantId、expectedHash |
| 2A | 等链接过期后尝试下载 | HTTP 401/403/410 | “下载授权已过期；请重新查询同一任务。” | 旧grant不能再次使用 |
| 3A | 用户重新查询同一taskId | `task_get`→新grant | “已签发新的短时授权。” | 新grantId、同artifactHash |
| 4A | 下载并核对Hash一致 | HTTP | 成功出口 | actualHash=expectedHash |
| 2B | 另一次测试中故意修改下载副本一个字节 | 本地Hash检查 | Codex必须判“制品不可信”，不得执行或挂载 | actualHash≠expectedHash |
| 3B | 删除损坏副本，重新签发并下载 | 新grant | Agent不应让用户忽略Hash差异 | 新副本Hash一致 |

Hash不一致不得用文件名、大小或“能够打开”替代完整性校验。

### 8.28 F-024：查询调度→精确确认→停用→重启后仍停用

目标出口：调度稳定停用。

| 步骤 | 人类或系统实际动作 | 预期节点/MCP | 模拟Agent可见回答与状态 | Codex验收证据 |
|---|---|---|---|---|
| 1 | 用户发送“停用调度`<scheduleId>`” | 分类=`SCHEDULE_DISABLE`→`schedule_get`/journey准备 | “将停用编号为…、绑定脚本Hash为…的唯一调度。” | scheduleId、proposalHash |
| 2 | Agent展示精确影响和按钮语义 | `确认唯一冻结提案` | “proceed：停用这一个调度；reject：保持原调度。” | CONFIRM_EXACT |
| 3A | 用户先点击`reject` | 决定提交拒绝 | “未停用，原调度保持ACTIVE。” | schedule状态不变 |
| 4A | 用户重新发送停用请求，Agent重新展示提案 | 新proposal | 不复用已拒绝proposal | 新proposalId |
| 5A | 用户点击`proceed` | `schedule_disable` | “调度已停用。” | 状态DISABLED、版本递增 |
| 6A | 停止并重启平台后查询 | `schedule_get` | 调度仍DISABLED，不再触发任务 | SQLite持久化证据 |

未知scheduleId、版本冲突或已经停用：不得创建新的“停用成功”假记录；应返回明确状态并保持幂等。

### 8.32 本节最终判定

本节补齐后，账本不再只是一组离散节点说明，而由两层组成：

```text
R-001..R-074：节点级等价类、错误和修复接点
F-001..F-024：从入口到稳定出口的连续人机旅程
F-xxx+I-yy：把服务、模型、文件、用户和重启中断插入连续旅程
```

当前实现仍不能通过所有72条运行：

- 无图片自然语言主干可以作为首条真实正向验收。
- 文件和视频可以进入附件导入，但必须用真实状态与产物核验是否走完后续作者化。
- 任意“主输入＋补充图片”在图片编排处仍应判`BLOCKED`。
- U盾/验证码等人工验证在Flowise恢复路由处仍应判`BLOCKED`。
- 候选超过45秒时仍可能没有对话出口，应判`BLOCKED`。

因此，Codex的正确操作不是遇到上述阻断便停止全部验收，而是：

1. 在对应`F-xxx`记录实际阻断和证据。
2. 继续执行其他不依赖该阻断的连续旅程。
3. 修复后仅从该剧本标明的稳定接点继续。
4. 最终只有72条运行都获得PASS，或每个BLOCKED都有已批准的明确豁免，才能宣称连续全链验收完成。
