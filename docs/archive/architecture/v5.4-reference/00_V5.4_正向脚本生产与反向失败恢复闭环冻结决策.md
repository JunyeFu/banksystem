# V5.4 正向脚本生产与反向失败恢复闭环冻结决策

> 文档版本：5.4.0  
> 生效范围：总体架构、阶段一、阶段二、阶段三、阶段四  
> 状态：冻结  
> 上一版本：V5.3 手写设计冻结版  
> 本次核心变化：把“脚本失效后重新生产”升级为项目一级业务主线，并冻结主动通知与两路径恢复协议。

---

# 1. 项目双向定义

## 1.1 项目正向

```text
用户输入成功回归案例
→ HiAgent/Coze 对话确认
→ 主控 LLM + RAG + Prompt Harness
→ FullActionPlan
→ MidsceneContextWindowControlLayer
→ Midscene + Playwright 真实页面复刻和事实采集
→ PlaywrightScriptPackage
→ 独立 Playwright 验证
→ Baseline 匹配
→ 用户选择：
   1. 输出脚本
   2. 挂载定时/周期回归任务
```

正式命名：

```text
ForwardAuthoringFlow
```

## 1.2 项目反向

```text
定时/周期 RegressionRun 失败
→ 创建 RegressionFailureIncident
→ 暂停失败 Schedule 或隔离失败 ScriptArtifact
→ 在 HiAgent/Coze 对话内主动提醒
→ 可选系统通知/弹窗/企业 IM
→ Agent 明确给出两条且仅两条恢复路径
```

正式命名：

```text
ReverseRecoveryFlow
```

两条恢复路径：

```text
路径一：
ABANDON_AND_REENTER_SUCCESS_CASE
放弃当前失败脚本
→ 保留旧脚本和失败证据
→ 用户重新输入一个已经人工成功的回归案例
→ 从 ForwardAuthoringFlow 起点重新生产

路径二：
DESCRIBE_CHANGE_AND_REAUTHOR
用户用自然语言描述页面、业务或操作流程变化
→ 主控 LLM 生成 ChangeImpactAssessment
→ 主控 LLM 生成 BehaviorPlanPatch
→ Prompt/Plan Harness 校验
→ 形成新的 FullActionPlanVersion
→ Midscene 重新视觉复刻并记录信息
→ 重新生成 PlaywrightScriptPackage
→ Playwright 独立验证
→ Baseline 匹配
→ 用户再次选择输出脚本或挂载定时任务
```

# 2. 冻结业务原则

## 2.1 失败后必须主动通知

定时或周期任务进入以下终态时：

```text
FAILED
TIMED_OUT
SYSTEM_ERROR
BASELINE_MISMATCH
SECURITY_BLOCKED
```

系统必须创建 `RegressionFailureIncident`，并立即进入通知链。

强制通知渠道：

```text
AGENT_CONVERSATION
```

可选增强渠道：

```text
AGENT_NOTIFICATION_INBOX
WEB_PUSH
DESKTOP_TOAST
ENTERPRISE_IM
EMAIL
```

“立刻”在工程上定义为：

```text
运行结果持久化和 FailureIncident/NotificationOutbox 写入：同一事务
通知 Worker 可见目标：≤ 2 秒
首个 Agent 对话投递尝试目标：≤ 5 秒
Agent 对话通知投递 P95 目标：≤ 30 秒
```

上述为系统目标，平台限流、网络中断或租户能力可能导致延迟；必须通过重试和备用渠道补偿。

## 2.2 失败后不得自动修复

禁止：

```text
RegressionRun 失败
→ LLM 自动修改正式脚本
→ 自动覆盖旧脚本
→ 自动恢复 Schedule
```

必须：

```text
RegressionRun 失败
→ 主动通知
→ WAITING_USER_RECOVERY_DECISION
→ 用户明确选择两条路径之一
```

## 2.3 两条路径是外部协议

对话中必须呈现：

```text
路径 1：放弃当前失败脚本，重新输入成功回归案例
路径 2：描述页面/业务/操作变化，重新视觉复刻并生成脚本
```

平台支持交互卡片时，可以显示两个按钮；否则以严格编号文本展示。

不得增加模糊的第三路径，例如：

```text
自动修复
忽略后继续运行
直接修改正式脚本
仅更新 Locator 后恢复
```

环境故障等非脚本问题可以执行基础设施重试，但只要任务最终失败并进入用户恢复流程，仍统一使用两路径协议。

## 2.4 旧资产不可覆盖

旧对象必须保留：

```text
旧 ScriptArtifact
旧 FullActionPlanVersion
旧 BaselineDefinition
失败 RegressionRun
FailureExplanation
失败 Trace/Evidence
用户 RecoveryDecision
```

新生成对象使用新版本和新 ID。

## 2.5 路径二不得直接改脚本

正确链：

```text
自然语言变化描述
→ BehaviorChangeRequest
→ ChangeImpactAssessment
→ BehaviorPlanPatch
→ FullActionPlanVersion N+1
→ Midscene 重新复刻
→ 新 StepTrace/ReplicationTrace
→ 新 ScriptGenerationContext
→ 新 PlaywrightScriptPackage
```

错误链：

```text
自然语言变化描述
→ 主控 LLM 直接编辑旧 *.spec.ts
→ 跳过 Midscene
→ 直接恢复 Schedule
```

## 2.6 默认完整复刻

路径二默认从入口重新执行完整 `FullActionPlanVersion N+1`。

只有同时满足以下条件，才允许增量复刻：

```text
ChangeDependencyAnalyzer = SAFE_FOR_SEGMENT_REPLAY
前置状态可确定性重建
受影响步骤边界明确
Baseline 可分段验证
高风险动作门禁仍完整
人工批准增量模式
```

首期实现只支持完整复刻，降低状态残留和依赖遗漏风险。

# 4. 正反向状态机

## 4.1 ForwardAuthoringFlow

```text
CASE_RECEIVED
→ REQUIREMENTS_CONFIRMED
→ PLAN_VALIDATED
→ REPLICATION_PASSED
→ TRACE_COMPLETE
→ SCRIPT_GENERATED
→ INDEPENDENT_VALIDATION_PASSED
→ BASELINE_MATCHED
→ SCRIPT_VALIDATED
→ WAITING_USER_DELIVERY_DECISION
→ OUTPUT_DELIVERED | SCHEDULE_MOUNTED
```

## 4.2 ReverseRecoveryFlow

```text
REGRESSION_RUN_FAILED
→ FAILURE_INCIDENT_OPENED
→ SCHEDULE_PAUSED
→ NOTIFICATION_QUEUED
→ AGENT_NOTIFICATION_ATTEMPTED
→ AGENT_NOTIFICATION_DELIVERED
→ WAITING_USER_RECOVERY_DECISION
```

路径一：

```text
ABANDON_AND_REENTER_SUCCESS_CASE_SELECTED
→ FAILED_SCRIPT_ABANDONED
→ WAITING_NEW_SUCCESS_CASE
→ NEW_CASE_RECEIVED
→ ForwardAuthoringFlow
```

路径二：

```text
DESCRIBE_CHANGE_AND_REAUTHOR_SELECTED
→ CHANGE_DESCRIPTION_RECEIVED
→ CHANGE_IMPACT_ASSESSED
→ PLAN_PATCH_GENERATED
→ PLAN_PATCH_VALIDATED
→ FULL_ACTION_PLAN_VERSION_CREATED
→ REPLICATION_QUEUED
→ REPLICATION_PASSED
→ TRACE_COMPLETE
→ SCRIPT_REGENERATED
→ INDEPENDENT_VALIDATION_PASSED
→ BASELINE_MATCHED
→ SCRIPT_VALIDATED
→ WAITING_USER_DELIVERY_DECISION
→ OUTPUT_DELIVERED | SCHEDULE_REPLACED_AND_RESUMED
```

# 5. 主动通知架构

```text
Regression Worker
→ RegressionRunResultService
→ 同一数据库事务：
   1. 保存 FAILED 结果
   2. 创建 RegressionFailureIncident
   3. 暂停 RegressionSchedule
   4. 写入 AgentNotificationOutbox
→ NotificationDispatcher
→ AgentPlatformNotificationPort
→ HiAgent/Coze Conversation
→ 可选 SystemNotificationPort
```

## 5.1 AgentPlatformNotificationPort

```ts
export interface AgentPlatformNotificationPort {
  sendFailureNotification(
    binding: AgentConversationBinding,
    notification: AgentFailureNotification,
  ): Promise<NotificationDeliveryResult>;
}
```

## 5.2 SystemNotificationPort

```ts
export interface SystemNotificationPort {
  send(
    channel: Exclude<NotificationChannel, 'AGENT_CONVERSATION'>,
    destinationRef: string,
    notification: AgentFailureNotification,
  ): Promise<NotificationDeliveryResult>;
}
```

## 5.3 可靠投递

```text
NotificationOutbox
→ Claim + Lease
→ Agent Conversation
→ Delivered / Retry
→ Fallback Channel
→ Dead Letter
→ 人工运维告警
```

幂等键：

```text
incidentId + notificationType + recipientUserId
```

同一失败事件不得在同一渠道重复产生多个对话提醒。

## 5.4 平台能力边界

Coze Studio 开源代码存在 Trigger、Notice 和 AsyncResult 等推送消息分类，也存在六字段 Cron 触发配置。这证明“被触发或异步结果进入对话消息流”在 Coze 架构中有真实基础。

但以下能力仍必须在企业租户逐项验证：

```text
服务端主动向指定 conversationId 推送消息
无活跃会话时创建通知会话
交互卡片和按钮
系统级弹窗
Web Push
企业 IM
消息送达/已读回执
```

因此 V5.4 以 `AgentPlatformNotificationPort` 隔离平台差异，不把某一租户的具体推送 API 写死在核心领域层。

# 6. 路径一详细规则

```text
用户选择：放弃当前失败脚本
```

系统执行：

1. 将旧 ScriptArtifact 标记为 `ABANDONED_AFTER_FAILURE`；
2. 保留旧脚本文件和所有 Hash；
3. 保持失败 Schedule 为 `PAUSED_WAITING_REAUTHORING`；
4. 不复用旧动作计划作为新案例事实；
5. Agent 提示用户重新输入或上传一个人工成功案例；
6. 新案例创建新的 `RegressionCaseVersion` 和 `AuthoringGoal`；
7. 新脚本验证通过后，用户决定：
   - 仅输出；
   - 替换旧 Schedule 中的 ScriptArtifact 并恢复；
   - 创建新 Schedule；
8. 旧 Schedule 与新 ScriptArtifact 的替换关系必须审计。

# 7. 路径二详细规则

```text
用户选择：描述变化并重新生成
```

Agent 必须追问并结构化确认：

```text
发生变化的页面或业务环节
变化前行为
变化后行为
是否新增/删除步骤
输入数据是否变化
成功终态是否变化
是否涉及高风险提交动作
是否有新的成功视频或截图
```

主控 LLM 输出：

```text
ChangeImpactAssessment
BehaviorPlanPatch
UnresolvedItems
```

Harness 检查：

```text
Patch 只能引用存在的 stepId
新 Action 必须符合 AtomicAction Schema
高风险动作必须重新评级
Plan 图必须可达且无环
成功终态必须存在
FixtureRef 必须有效
RAG 证据必须可追踪
```

通过后：

```text
旧 FullActionPlanVersion 保留
→ 应用 Patch
→ 创建新 FullActionPlanVersion
→ 完整 Midscene 视觉复刻
→ 全量 Playwright 事实采集
→ 新脚本
→ 独立验证
→ 用户交付选择
```

# 8. 用户对话协议

失败提醒示例：

```text
定时回归任务“每周三支付回归”执行失败。

失败分类：页面视觉结构变化
失败步骤：点击“确认转账”
当前脚本版本：SCRIPT-001@1.3.0
任务已暂停，避免重复失败。

请选择恢复路径：
1. 放弃当前失败脚本，重新输入一个人工成功的回归案例。
2. 描述页面或操作流程发生了什么变化，我将重新生成行为清单、
   调用 Midscene 视觉复刻、记录事实并重新生成 Playwright 脚本。
```

路径二输入示例：

```text
确认转账按钮现在改成了“提交”，点击后增加了一个短信验证码页面，
输入测试验证码后才会显示转账成功。
```

Agent 返回计划 Diff：

```text
S03 REPLACE：点击“确认转账”
→ 点击“提交”

S04 ADD：输入短信验证码
S05 ADD：点击“确认验证码”
原终态验证移动到 S06
```

高风险 Patch 必须先展示计划 Diff 并取得确认，之后才进入 Midscene 复刻。

# 9. 调度策略

默认失败策略：

```text
PAUSE_ON_TERMINAL_FAILURE_AND_NOTIFY
```

Schedule 状态：

```text
ACTIVE
→ TRIGGERED
→ RUN_FAILED
→ PAUSED_WAITING_USER_RECOVERY
```

恢复：

```text
路径一新脚本通过
或
路径二新脚本通过
→ 用户确认替换 ScriptArtifact
→ SCHEDULE_ARTIFACT_REPLACED
→ ACTIVE
```

禁止失败 Schedule 在等待用户决策期间继续周期触发。

# 11. V5.3 到 V5.4 的变化

| V5.3 | V5.4 |
|---|---|
| 脚本失效后创建 ReauthoringRequest | 建立完整 ReverseRecoveryFlow |
| 通知为泛化平台能力 | Agent 对话主动提醒成为强制需求 |
| 重新生产路径未严格限定 | 冻结为且仅为两条路径 |
| 失败后 Schedule 行为未完全冻结 | 默认自动暂停并等待用户 |
| 用户描述变化后重新生产概念化 | 新增 ChangeImpactAssessment 和 BehaviorPlanPatch |
| 可理解为修复旧脚本 | 明确禁止直接修改旧脚本 |
| 正向链为主要叙述 | 正向和反向均为一级业务主线 |
| 通知平台细节分散 | 新增 AgentPlatformNotificationPort 和 NotificationOutbox |
| 恢复完成后行为未统一 | 回到用户选择输出或重新挂载 Schedule |

# 12. Definition of Done

V5.4 正反向闭环完成必须满足：

```text
[ ] 正向输入到 SCRIPT_VALIDATED 完整
[ ] SCRIPT_VALIDATED 后可输出或挂载 Schedule
[ ] 定时失败自动创建 RegressionFailureIncident
[ ] 失败事务同步写入 NotificationOutbox
[ ] Agent 对话主动提醒可用
[ ] 可选通知渠道至少完成一个 Adapter
[ ] 失败 Schedule 自动暂停
[ ] 对话严格显示两条恢复路径
[ ] 路径一能重新接收人工成功案例
[ ] 路径二能生成 ChangeImpactAssessment
[ ] 路径二能生成并校验 BehaviorPlanPatch
[ ] 路径二必须重新 Midscene 复刻
[ ] 新脚本必须独立 Playwright 验证
[ ] 用户可重新选择输出或挂载
[ ] 旧脚本、旧计划和失败证据不可覆盖
[ ] 通知、选择、Patch、复刻、验证和恢复全部可审计
```
