# 01 立项与治理文书

## 阶段目标

把业务构想转化为可审议、可追溯、可控风险的项目授权。商业银行的信息科技治理要求董事会/高管层对信息科技战略和风险管理承担相应责任，因此项目不能只有开发任务单；必须留下范围、风险、数据和责任的正式记录。

## 最小文书包

| 文书 | 必填内容 | 责任与批准 |
|---|---|---|
| 项目建议书/立项申请 | 背景、问题、目标、收益、范围、预算级别、依赖、替代方案 | 发起部门；业务、科技、风险/合规会签 |
| 可行性研究与方案比选 | 业务、技术、数据、安全、成本、交付能力、退出方案 | 项目经理；架构、安全、采购/财务复核 |
| 项目章程 | 发起人、项目经理、治理机构、范围边界、里程碑、成功标准、升级机制 | 发起人批准 |
| 数据与安全初评 | 数据分类、个人信息/重要数据判断、最小化原则、访问边界、日志与留存 | 数据/安全责任人批准 |
| 风险登记册 | 风险描述、概率、影响、责任人、控制措施、触发条件、剩余风险 | 项目经理维护；风险责任人确认 |
| RACI 与沟通计划 | 决策、执行、咨询、知会角色；例会、周报、重大事项升级 | 项目经理批准 |

## 本项目适配

- 目标系统与测试平台分别建账：银行核心范围、自动化测试范围、演示数据范围不得混写。
- 立项即固化“不直写 Fineract 数据库、只通过 Gateway/受控 Test Support API”的边界。
- AI 能力仅写为辅助作者化与检索能力；不得把 GPT 输出认定为审批结论、测试通过或账务事实。

## 审核清单

1. 是否有明确的业务负责人、技术负责人、风险/安全负责人和验收负责人？
2. 是否列出不做什么、不可触碰的数据/系统，以及失败时的停机与回退边界？
3. 是否将需求、风险、变更、测试和验收证据关联到唯一项目编号？
