# 03 需求、设计与开发文书

## 阶段目标

使每个业务要求可从来源追溯到设计、实现、测试、上线和验收，避免“开发完成但无法证明满足需求”。

## 最小文书包

| 文书 | 建议结构 | 与本项目的关联 |
|---|---|---|
| BRD/业务需求说明 | 背景、流程、角色、规则、异常、监管/合规、验收指标 | 账户查询、转账、贷款等业务链路 |
| PRD/需求规格说明 | 范围、原型、字段、状态机、权限、非功能、可追溯编号 | Gateway/API/门户可验证需求 |
| 需求追踪矩阵 | 需求 ID、来源、设计、代码/PR、测试、证据、版本、状态 | Quality Case 与 Baseline 的基础输入 |
| 总体设计说明 | 上下文、组件、部署、数据流、边界、可观测性、容灾 | Fineract 唯一账务事实源与渠道边界 |
| 详细设计说明 | 模块、接口、数据模型、校验、错误码、幂等、权限、审计 | Bank Channel Service 与平台服务 |
| 接口/数据契约 | OpenAPI、Schema、字段口径、脱敏、版本兼容、错误处理 | 受控 Test Support API 与平台契约 |
| 安全/隐私设计 | 身份、授权、最小权限、密钥、日志、数据保留、威胁建模 | 禁止密钥进入文档/RAG，模型无工具权限 |
| 配置与变更记录 | 基线、差异、审批、影响分析、回退、验证结果 | 版本、Compose、数据库迁移和发布 |

## 文控要求

- 标题页必须标明：文书类型、项目名称、项目编号、密级、版本、状态、编制/复核/批准、日期。
- 正文页必须有文档编号、版本、页码和受控副本标识；不可在页眉页脚放真实客户或密钥。
- 每个需求和接口均使用稳定 ID；测试结果、截图、Trace 和证据哈希引用该 ID，不以文件名代替关系。

## 本项目格式建议

使用红、白、黑三色：黑色为正文/主标题，深红仅用于章节与风险提示，白色作为主体；不使用任何第三方银行 Logo、色板、封面或版式。详细 Token 见 `06-文书格式与生成规范.md`。
