# 调度与失败接管

## 业务目标
调度与失败接管，以[正式需求](../../../../../design/product-normalization/requirements.md)的对应验收为准。

## 输入与输出
输入当前合同、既有控制与用户确认；输出源码/文书和对应证据。

## 实现

### S2-1 调度可达性与零自动重试（2026-10-09）

业务：测试人员从一个当前身份下已经成功并持证的 Journey 创建固定版本回归调度，不重新生成脚本；能从 CLI 查询与明确停用，失败后查看原事故。新建调度不自动重试；失败暂停机制保留。现有保留调度不由本任务自动改写。

1. 核对并修正 Journey 执行计划与 MCP schedule_create 的 maxRetries=0；先打开 Harness/MCP，验证正常周期/一次性合同及失败暂停的既有测试。
2. 关闭 Harness/MCP，打开 CLI/Controller。新增 hz-agent schedule create <sourceJourney> --session <freshSession> --cron <five-field-cron> --timezone <IANA> --jsonl，或以 --at <offset-ISO> 替代 --cron；schedule status <id>、schedule disable <id> --session <id> --reason <text> --jsonl；failure show <incident>。Controller只增加既有schedule_get/failure_get的只读方法；从公开 MCP 复用 validatedJourneyId、EXECUTION_PLAN、精确执行决定与 schedule_create，绝不直写 Harness/SQLite。源证据或身份不匹配时，在创建前失败；重复命令绑定原会话/计划而非新建调度。
3. 最小验证：Node24 headless-cli 与新 schedule 合同；Node20 TypeScript、既有 scheduler/lease 合同；真实 MCP/Harness 临时 SQLite 验证创建固定版本、重复命令、查询与停用。测试专用模型和临时库不算 LIVE。产品 npm.cmd run check:tests、python scripts/architecture/validate_refactoring.py --batch RF-064、python scripts/docs/validate_docs.py；证据入本批索引，S2 仍等待异常接管及真实运行。

路径：agent-cli/src/contracts.mjs、headless-app.mjs、production-service.mjs、agent-cli/test；mcp/src/server.cjs；harness/src/i10/service.ts；既有 scripts/verification；本批控制文件、唯一顺序及 backlog。公开返回只含调度版本/状态/脚本绑定、事故摘要和工件引用，不输出脚本全文、凭据或本机路径。不得新增人工提案门、备用路径、模型调度或不经验证激活。

### S2-2 持久化调度单链与故障暂停（2026-10-09）

先在既有 journey-evidence-verifier.test.cjs 复用受验证来源夹具，启动真实 Harness HTTP 与 MCP（临时 SQLite、测试专用工件与会话，不接触保留状态）。从实际 CLI production service 调用创建/重放，数据库核对同一冻结脚本与唯一调度；推进隔离库时钟触发一次，实际领取任务并提交受控失败，验证原调度PAUSED_FAILURE、事故和工件回读，以及后续tick不再触发。显式停用不得覆盖原失败或新增运行。先打开 Harness/CLI；测试替代的是银行浏览器结果，不替代 Harness/MCP/SQLite。此门记为 INTEGRATION，非银行/BYOK/周期LIVE；验证码和人机接管仍归下一垂直片。
已观察来源：claimNextRun 将所有过期 RUN_EXECUTE 重置为 QUEUED，未读取 schedules.max_retries，绕过本批零重试规则。追加反例后修复仅零重试调度：原任务 FAILED、运行 BLOCKED（沿用既有存储状态合同），原执行 FAILED，周期调度暂停并登记可回读事故，要求人工确认实际业务状态；一次性保持终止，不造截图或新运行。保留原执行证据、拒绝旧租约晚完成；无调度或历史允许重试的既有路径不在本片自动迁移。验证同一事故只产生一次、下次领取 EMPTY、历史租约回收合同不受影响。

从已有schedule/failure工具核对CLI可达性；测试单次触发、失败暂停、原运行恢复与合成验证码接管，不重引入提案批准。
每个具体验收垂直切片控制1—3天；S2/S3先检查已有实现再补最小差异。路径白名单：platform/hengzhun-regression-system/agent-cli, platform/hengzhun-regression-system/mcp, platform/hengzhun-regression-system/harness, platform/hengzhun-regression-system/worker。

### S2-3 验证挑战 CLI 与原浏览器接管（2026-10-09）

已观察缺口：Worker/Harness 已有验证挑战、版本条件决定与原浏览器等待，但 CLI 无可达入口。先打开 CLI/Controller，在现有工具合同上增加 verification status <challengeId> 及 verification ready|confirm|cancel <challengeId> --session <sessionId> --revision <当前版本> --jsonl。对应 USER_READY、USER_ACTION_COMPLETED、CANCEL，不接收验证码/PIN/自由说明，不触发新运行。写操作须当前身份、本地会话及明确版本，读投影只含挑战ID、任务ID、类型、状态、版本与期限。

验证先用已有 schedule.test.mjs 注册入口补 CLI/工具合同、陈旧版本拒绝及信息隔离；Controller只新增verification_get只读方法。随后关闭Controller、打开Harness，复用现有临时SQLite/MCP集成夹具验证真实决定链与同任务恢复；合成验证码在隔离Chromium中验证原页面完成后才继续，取消/会话丢失不重执行。复用既有验证框架，不新增依赖、银行路由或迁移；所有结果记INTEGRATION，仍不代表机构验证码/BYOK LIVE。源路径沿用S2白名单，完成后回填索引/唯一顺序/backlog/外部站点。

真实SQLite反例发现正式i8-formal-runner及作者化UKey接管上报USER_ASSISTED，违反verification_type枚举；UKey修正为UKEY，泛人工确认用已有MANUAL_APPROVAL。Worker登记还缺detectionSummary并多传attempts，按现有严格HTTP合同投影，并登记明确10分钟期限。此阶段关闭Harness/Controller，打开CLI/Worker；加入真实HTTP报告及原页面合同反例，合成验证码夹具使用CAPTCHA，不向银行生产链增加验证码功能。
