# 复兴银行与衡准平台受控重构全过程规范

## 1. 文档定位

本文件规定复兴银行业务系统与衡准自动化回归测试平台的重构全过程、批次门禁、证据要求、切流与回滚控制。它回答“获准执行的重构批次必须怎样做”，不决定“项目下一步先做哪个批次”。

项目实施顺序仍唯一受 [`v54-implementation-batches.md`](../../agent/plans/active/v54-implementation-batches.md) 控制；待办状态仍登记在 [`agent/backlog.yaml`](../../agent/backlog.yaml)。任何重构任务只有被唯一实施顺序文档明确授权后才能进入执行状态。本文件不得被解释为第二套排期。

## 2. 重构目标与非目标

### 2.1 目标

- 消除职责重叠、重复状态机、跨层隐式依赖和不一致命名。
- 在不改变已验收业务语义的前提下建立稳定模块边界。
- 让每个变更都能被定位、验证、回滚和追责。
- 让银行端、Flowise、Harness、Worker、SQLite、Midscene 和 Playwright 各自只承担其权威职责。
- 形成可持续的模块合同、测试资产、运行证据和发布门禁。

### 2.2 非目标

- 不借重构新增银行业务、扩大产品范围或重写全部系统。
- 不以“代码更整洁”为由改变已冻结的API、状态机或用户流程。
- 不把历史计划、静态测试或模拟结果包装为当前运行证据。
- 不在一个批次中同时重构银行核心、身份认证、Flowise、Harness 和 Worker。
- 不以删除历史证据、迁移记录或回退制品换取表面整洁。

## 3. 固定系统边界

| 板块 | 权威职责 | 禁止越界 |
|---|---|---|
| 复兴银行核心/Fineract | 账户、余额、交易、贷款等账务事实 | 不存衡准任务、模型上下文或脚本证书 |
| 银行Channel/门户 | 页面交互、银行接口聚合、身份映射 | 不直接控制Flowise或Worker内部状态 |
| Keycloak | 用户、会话、角色和认证 | 不承载银行业务状态 |
| Flowise | 唯一自然语言入口、主控工作流、人工门槛 | 不直接访问文件系统、SQLite或浏览器 |
| Harness | 合同校验、Journey、状态机、幂等、调度、证据与审计 | 不承担开放式自然语言推理 |
| Worker | 受控任务执行、Builder、浏览器驱动和证据采集 | 不改变项目源码或业务数据库 |
| Midscene | 视觉定位、页面理解和候选定位恢复 | 不直接签发正式脚本，不直接执行业务点击 |
| Playwright | 确定性点击、输入、断言、取证和正式回归 | 不猜测用户意图 |
| Harness SQLite | 衡准权威业务状态和不可变执行记录 | 不存明文凭据 |
| Flowise SQLite | Flowise自身配置和运行元数据 | 不作为衡准业务权威库 |

任何职责变化必须先形成决策记录、迁移方案和回滚方案，再进入实现批次。

### 3.1 目标结构原则

- `bank-channel-service`继续执行 [`ADR-002`](adr/adr-002-modular-monolith.md)，不得在边界稳定前拆分新微服务。
- 衡准在单一产品目录内按输入摄取、案例与Journey、凭据、作者化、脚本、执行、调度、证据、修复划分逻辑模块；Flowise、Harness、MCP和Worker是运行角色，不代替业务模块。
- 每个可部署单元内部优先采用模块化单体；新增独立服务必须有ADR证明网络隔离、独立扩缩容或故障隔离收益超过部署和一致性成本。
- 模块只能暴露一个登记的公开出口；跨模块调用不得导入对方内部文件或直接访问对方数据表。
- 重构基本单位是端到端业务能力，不是目录、单个类或通用工具函数。

### 3.2 模块内部四层

新建或完成迁移的业务模块采用以下逻辑层；现有框架可映射而不要求机械改名：

```text
interface → application → domain
infrastructure → application/domain定义的端口
```

- `domain`：实体、值对象、领域规则、事件和不变量，不依赖数据库、HTTP、UI、文件系统或框架对象。
- `application`：用例编排、事务意图和端口，不包含具体存储或网络实现。
- `infrastructure`：Repository、第三方API、消息、文件和运行时适配器。
- `interface`：HTTP、CLI、定时任务、消息消费者、UI和MCP入口。

依赖规则以 [`refactoring/dependency-rules-v1.md`](refactoring/dependency-rules-v1.md) 和机器校验器为准，不能只依赖代码评审。

## 4. 证据优先级

发生冲突时按以下顺序裁决：

1. 当前运行环境产生的可复现 `LIVE_E2E` 证据。
2. 当前分支代码、数据库迁移、公开合同及其测试结果。
3. 当前能力矩阵、决策记录和本规范。
4. 历史发布目录、历史验收账本和历史设计文档。
5. 口头描述、截图推断和计划性表述。

静态通过、Mock、旧进程健康、文件Hash正确或历史PASS均不能单独证明重构完成。

### 4.1 观察行为分类

特征测试记录的是当前行为，不自动代表正确行为。每项观察必须归类：

- `EXPECTED_CONTRACT`：经合同或负责人确认，目标实现必须保持。
- `LEGACY_COMPATIBILITY`：当前调用方依赖，需通过适配器和退出窗口迁移。
- `CONFIRMED_DEFECT`：已确认缺陷，不得固化为目标行为。
- `UNKNOWN_BEHAVIOR`：证据不足，必须形成决策后才可迁移。
- `INTENTIONAL_CHANGE`：经版本化合同、迁移和回滚方案批准的行为变化。

禁止用快照测试把 `CONFIRMED_DEFECT` 或 `UNKNOWN_BEHAVIOR`直接提升为目标合同。

## 5. 重构批次状态机

每个重构批次必须使用唯一编号 `RF-<三位序号>`，并依次经过：

```text
PROPOSED
→ BASELINE_FROZEN
→ CONTRACT_APPROVED
→ IMPLEMENTING
→ SHADOW_VERIFIED
→ CUTOVER_READY
→ CUTOVER
→ OBSERVING
→ ACCEPTED
→ CLEANUP_ELIGIBLE
→ CLOSED
```

异常状态：

- `BLOCKED`：存在外部依赖或用户决策阻断，停止扩大修改面。
- `ROLLED_BACK`：已执行回滚，保留失败证据和恢复结果。
- `SUPERSEDED`：被新批次替代，但不得删除历史证据。
- `ABORTED`：批准前终止，不得残留运行态或半迁移数据。

不得跳过 `BASELINE_FROZEN`、`CONTRACT_APPROVED`、`SHADOW_VERIFIED` 或 `CUTOVER_READY`。

## 6. 批次合同与目录

每个获准批次应在 `docs/architecture/refactoring/batches/RF-xxx/` 保存：

```text
batch.yaml
baseline.md
target-design.md
contract-delta.md
verification-plan.md
cutover-runbook.md
rollback-runbook.md
evidence-index.md
decision-log.md
```

`batch.yaml`至少包含：

  include_paths: []

## 7. 修改预算与并发限制

批次批准前必须设定并执行：

- 最大修改文件数。
- 最大新增/删除代码行数。
- 最大合同变更数。
- 最大数据库迁移数。
- 最大同时开放模块数。
- 允许的服务停机窗口。
- 预计回滚耗时上限。

默认只允许一个批次处于 `CUTOVER`，最多两个互不共享合同和数据库的批次处于 `IMPLEMENTING`。共享同一数据库表、公开API、Agentflow或运行端口的批次禁止并行切流。

## 8. 全过程门禁

### RC-D0 方向细化前置门禁（执行拦截）

任何重构执行请求（用户以提示词直接要求“执行/实现/继续/完成”某一重建阶段）在满足四级细化链之前，执行方必须拦截：不修改任何文件、不运行任何实施命令，只向用户说明缺失层级并引导补全。

四级细化链（大方向 → 小方向，任何一级缺失或含糊即视为未细化）：

1. 实施顺序：`agent/plans/active/v54-implementation-batches.md` 已明确授权该阶段（唯一顺序源，backlog 状态不能替代）。
2. 批次：`batches/RF-xxx/batch.yaml` 已定义单一变化轴、写入白名单、修改预算与回滚点。
3. 切片/细链：已定义单业务目标、单功能点，允许与禁止路径明确，不跨切片。
4. 任务包与命令级 done 条件：按 `agent-task-package-v1.md` 格式产出任务包，done = 具体命令的期望输出（可现场复算、端到端口径）。

拦截行为：

- 用户直接下达执行指令而上述层级缺失时，不执行、不改文件、不声称完成；
- 明确指出缺失层级及其应落位的证据位置；
- 引导用户先自上而下细化控制体系（大方向→小方向）；
- 用户细化完成后，进入 plan mode 输出任务细化方案（任务包 + done 条件 + 执行顺序 + 禁止事项），供用户批准；
- 用户批准细化方案后，才依次执行 RC-G0（工作区与身份快照）、RC-G1（代码考古）及其后门禁。

### RC-D1 逐级向上同步门禁（自底向上回灌）

任务包执行过程中一旦确定任何新细节，必须**立即**（在继续下一步骤或声明完成之前）逐级向上同步至顶层设计，不允许底层事实只在底层停留：

四级同步链（小方向 → 大方向，逐级传递，不得跳级或只同步到中间层）：

1. 任务包（`tasks/`）→ 切片（`slices/`）：决策结果、字段/别名事实、审计发现、预算消耗、风险变化，回写切片记录。
2. 切片 → 批次（`batches/RF-xxx/batch.yaml`）：范围变化、合同变更计数消耗、预算剩余、回滚点增补。
3. 批次 → 实施顺序（`agent/plans/active/v54-implementation-batches.md`）与目标设计/合同文档（`target-design.md`、`mcp-boundary-contract-v1.json`、`docs/design/**`）：事实性修正（如契约与可执行边界冲突时的自映射修正）、状态迁移、遗留项登记。
4. 全部同步条目在 `decision-log.md` 记录（日期、来源层级、影响范围、证据位置），保证任意顶层文档可追溯到具体任务包决策。

强制规则：

- 同步完成是任务包完成声明的前置条件；未完成逐级同步，不得将任务标记完成，也不得进入下一切片。
- 同步只写规划文档与合同事实，不扩大执行范围；任何因同步暴露的越界修改必须拆批，不得借同步顺势改码。
- 发现顶层设计（实施顺序/批次/目标设计/合同）与底层事实冲突时，以“契约跟随可执行边界、语义冻结”为原则修正顶层，并在同步记录中注明冲突与修正依据。
- 违反本门禁：暂停执行、先补同步、再继续；不得以“已完成”“已验证”覆盖缺失的同步记录。

### RC-G0 工作区与身份门禁

开始前必须记录：Git根目录、分支、HEAD、remote、dirty-tree清单、目标运行目录、ReleaseIdentity、服务PID与端口、数据库迁移版本、Agentflow版本及Hash。

通过条件：所有写入路径可追溯；用户既有改动已分类；回滚点可用。失败条件：Git根不明、运行权威不明、同一服务存在多个候选目录或脏改动归属不明。

### RC-G1 代码考古门禁

必须建立模块清单、入口、出边、数据库读写、环境变量、端口、外部合同、测试入口、运行脚本、重复实现和废弃候选清单。

每项发现标记为：`ACTIVE`、`SHADOW`、`LEGACY_REQUIRED`、`DEAD_CANDIDATE` 或 `UNKNOWN`。`UNKNOWN`未归零前不得删除代码。

事实资产必须落入 `docs/current-state/` 的系统总览、运行拓扑、模块、依赖、数据库、API、环境和风险八类清单。每条事实包含来源、核验时间及 `CONFIRMED/INFERRED/UNKNOWN` 状态；目录名或历史文档不能单独证明运行关系。

### RC-G2 行为基线门禁

冻结重构前的业务行为、API响应、数据库不变量、关键页面、失败语义、外部副作用和性能基线。基线必须同时记录命令、输入摘要、环境身份、起止时间、退出码、制品Hash和证据路径。

最低保护集不得只含一条细链：银行端必须覆盖登录、账户/交易查询、收款人、转账、验证和单号查询；衡准端必须覆盖自然语言、文件、视频、图片OCR、作者化、Builder、纯Playwright、2×2证书、激活、即时/定时执行和反向修复。适用项及证据要求见 [`refactoring/characterization-baseline-v1.md`](refactoring/characterization-baseline-v1.md)。

### RC-G3 目标边界门禁

目标设计必须明确模块所有者、输入、输出、状态归属、允许依赖、禁止依赖、同步/异步语义、超时、重试、幂等、审计、失败关闭和降级边界。

禁止使用“统一处理”“智能判断”“必要时重试”等不可验证表达；必须转换为字段、状态、错误码或可观测事件。

目标设计还必须登记模块公开出口、内部目录、表级写入权和依赖检查命令。没有机器可检查的依赖边界，不得宣称目标模块完成。

### RC-G4 批次范围门禁

每批只处理一个主要变化轴：职责迁移、合同统一、数据迁移、执行器替换或界面适配。若同时改变公开合同、数据库、状态机和执行器，必须拆批。

每个迁移批次同时只能对应一个端到端业务能力，并执行固定绞杀者顺序：保护旧行为→冻结新合同→建立新模块→旧入口适配→迁移纯规则→收口数据访问→新旧比较→切换主路径→观察→清理旧实现。技术变化轴用于限制批次，不得取代业务能力边界。

### RC-G5 实现验证门禁

至少通过：变更文件静态检查、单元测试、合同测试、迁移测试、失败注入、敏感信息扫描、兼容测试和相关E2E。测试不存在或无法运行时只能标记 `BLOCKED`，不能以人工推断替代。

### RC-G6 影子比较门禁

新旧实现用同一规范化输入并行执行，但旧实现仍拥有写权。比较项至少包括响应、状态转换、数据库副作用、Artifact Hash、错误码、时延和资源使用。

差异必须归类为：`EXPECTED`、`DEFECT_NEW`、`DEFECT_OLD`、`NON_DETERMINISTIC`、`ENVIRONMENTAL`。未解释差异不得进入切流。

### RC-G7 切流门禁

切流前必须满足：新实现证据通过；运行配置和数据库版本一致；回滚命令演练通过；旧实现仍可恢复；无未知进程/端口占用；用户可见影响明确。

切流必须使用配置、路由或版本指针，不允许删除旧实现后直接替换。

### RC-G8 观察门禁

切流后进入观察期，跟踪错误率、成功率、延迟、重试、队列积压、状态机卡点、数据库异常、浏览器资源和用户流程完成率。发生回滚触发条件时立即停止扩大流量。

### RC-G9 清理门禁

只有新实现已验收、观察期通过、回滚窗口结束、无引用证明成立、历史证据已归档后，旧实现才进入清理候选。删除前必须再次搜索代码、脚本、文档、Flowise定义、测试、环境变量和发布清单中的引用。

## 9. 高精细度控制项

### 9.1 API和事件合同

- 字段增加默认向后兼容；删除或改义必须版本化。
- 错误必须有稳定错误码、可读摘要、可恢复性和安全诊断引用。
- 所有写操作必须有幂等键、期望版本和冲突语义。
- 时间统一携带时区；金额使用明确币种和最小货币单位或定点表示。
- 日志不得记录认证头、API Key、密码、验证码、PIN或完整敏感请求体。

### 9.2 数据库

- Fineract保留账务权威；Channel库只保存渠道投影；Harness SQLite保存衡准状态；Flowise SQLite不升级为业务权威库。
- 迁移只前进，不修改已发布迁移；迁移必须可重复检测且失败关闭。
- 破坏性迁移采用“扩展→双写/回填→读切换→停止旧写→清理”顺序。
- 回填记录总数、成功数、失败数、校验Hash和重跑策略。
- 不可变审计表必须禁止更新和删除，修复用补偿记录表达。
- 新增数据库访问必须进入所属模块Repository；旧跨模块查询可以登记保留，但不得继续复制。
- 每张表必须登记权威模块、唯一写入方、允许读取方和迁移责任。跨模块读取仅允许应用服务、只读投影、领域事件、查询API或已登记组合查询层。

### 9.3 前端与身份

- 页面不得直接依赖数据库结构或Flowise内部字段。
- 身份由Keycloak声明和后端映射确定，前端显示信息必须来自当前会话对应的后端合同。
- 登录、客户资料、转账和验证页面重构必须保留可访问性名称、稳定测试标识和错误状态。
- UI视觉调整不得与认证协议、业务状态机迁移混在同一批次。

### 9.4 Flowise、Harness与Worker

- Flowise只负责交互与编排；系统外操作只通过受控MCP合同。
- Harness先校验后落库，任何MCP写操作不得绕过Journey版本和状态门槛。
- Worker只消费已冻结任务；任务版本、脚本Hash和证书Hash必须一致。
- Midscene只输出定位证据和候选目标；Playwright执行点击、输入和断言。
- 长任务必须异步提交并由任务状态/结果收件箱回读，禁止让对话同步等待终态。
- 普通案例不得因页面静态文案触发U盾；验证策略必须由动作、路由、DOM和业务证据共同决定。

### 9.5 变量与命名

- 通用模型变量使用 `CONTROL_*` 与 `VISION_*`；禁止供应商名扩散到业务合同。
- 标识符统一使用明确后缀：`Id`、`Ref`、`Hash`、`Version`、`Status`、`At`。
- 布尔变量使用肯定语义；禁止双重否定。
- 同一概念只允许一个权威字段名；旧名通过适配器兼容并登记删除窗口。
- 错误码格式为稳定域前缀加具体原因，禁止用一个泛化错误覆盖不同失败阶段。

### 9.6 AI执行边界

- AI不得自行扩大白名单、改写验收标准或跨越人工决策门槛。
- 先读取权威文档、合同和当前代码，再生成修改。
- 每次修改后立即运行最小相关测试；批次结束运行完整门禁。
- 三次出现同类失败必须停止盲目重试，形成根因记录并缩小问题面。
- 不得用Mock、旧证据、静态PASS或人工改清单冒充真实发布和E2E成功。
- 代码生成、测试执行、证据归档和完成判定必须由不同步骤完成，避免自证闭环。

### 9.7 AI代码债与文件治理

- 名称相似的实现不得直接合并；先比较调用方、输入输出、空值、时区、失败和副作用语义。
- 新增抽象必须满足至少一项：两个稳定实现、隔离第三方依赖、支持测试替换、代表明确业务概念或承担长期兼容合同。
- 未经批次合同解释，不得新增名为 `utils`、`helper`、`manager`、`base`、`common`、`misc`、`temp`、`new`、`v2` 或 `final` 的模糊文件/目录。
- 新文件必须有独立职责、明确调用方且无法合理归入现有模块；新依赖必须记录用途、许可证、离线可用性、供应链来源和移除成本。

### 9.8 固定Agent上下文与任务包

Agent执行重构前必须读取：仓库 `AGENTS.md`、本规范、模块边界、依赖规则、测试入口、迁移状态和当前批次合同。单次任务包必须明确目标、当前入口、允许/禁止路径、必须保持的合同、必跑命令、证据位置和完成定义；格式见 [`refactoring/agent-task-package-v1.md`](refactoring/agent-task-package-v1.md)。

### 9.9 提交与质量闸门

- 单个提交或PR只对应一个业务目标，不混合结构迁移和功能新增。
- 一般不超过25个文件且不同时修改三个以上业务模块；超出必须拆分或形成书面例外。
- 每个提交必须可独立回退；删除代码附引用检查；新增依赖和抽象附真实调用方。
- 批次验证矩阵必须列出格式、静态分析、类型检查、依赖边界、单元、合同、集成、E2E、构建、迁移和安全扫描的具体命令、预期退出码、证据及阻断属性。

## 10. 回滚控制

### 10.1 自动回滚触发条件

- 核心业务不变量被破坏。
- 错误率或超时率超过批次阈值。
- 出现数据丢失、重复记账、越权、凭据泄露或不可解释状态。
- 新旧影子结果出现未批准差异。
- 数据库迁移版本、运行代码和公开合同不一致。
- 无法在规定时间内定位失败阶段。

### 10.2 回滚步骤

1. 停止新流量和新写入。
2. 保存日志、数据库快照、任务状态和环境身份。
3. 按运行手册恢复旧路由/旧版本。
4. 校验旧实现健康和关键业务不变量。
5. 对新实现产生的数据执行已批准的补偿或兼容读取。
6. 记录回滚原因、影响范围、恢复时间和后续处置。

禁止通过删除数据库、清空日志、覆盖工作区或 `git reset --hard` 代替回滚。

### 10.3 观察阈值与恢复目标

批次必须在切流前冻结观察窗口、最小样本量、成功率/错误率/延迟阈值和审批人。默认观察期不得少于一个完整业务周期；本机演示系统没有稳定流量时，必须使用规定次数的确定性回放代替，不得以“运行一段时间”表述。

`maxRtoMinutes`定义恢复到旧主路径的最长时间；`maxRpoMinutes`定义可接受的数据恢复点损失。R3/R4批次必须演练恢复命令并保存起止时间、数据不变量和结果Hash。

## 11. 风险分级

| 等级 | 示例 | 必须控制 |
|---|---|---|
| R0 | 文档、注释、无行为命名清理 | 链接/格式校验 |
| R1 | 单模块内部重排 | 单元测试、差异检查 |
| R2 | 模块接口或Flowise节点变更 | 合同测试、影子比较、回滚点 |
| R3 | 数据库、认证、调度、浏览器执行变更 | 迁移演练、失败注入、E2E、人工切流 |
| R4 | 账务、权限、凭据或不可逆数据变更 | 独立审计、双重确认、备份恢复演练、禁止自动切流 |

风险取最高项，不因改动行数少而降级。

## 12. 启动判据与量化指标

出现重复核心规则、跨层字段连锁修改、职责不明、AI反复生成重复实现、测试不足、配置分散、删除引用不明等四项以上时，项目可提出系统性重构；是否启动仍由唯一实施顺序文档批准。

项目指标及口径以 [`refactoring/metric-catalog-v1.md`](refactoring/metric-catalog-v1.md) 为准。最低目标包括：已登记核心流程E2E覆盖率100%、循环依赖0、跨模块内部导入0、Controller直接数据库访问0、未登记环境变量0、无归属数据库表0、重复核心业务规则0、人工构建步骤0、核心API合同覆盖率100%、获准批次独立回滚率100%。每个指标必须有扫描范围、分母、命令、时间和证据，禁止只填写目标值。

## 13. 推荐的首轮批次

以下只是候选，不构成执行授权：

| 候选 | 范围 | 预期风险 |
|---|---|---|

| RF-001 | 统一衡准跨层字段、错误码和适配器，不改变运行语义 | R2 |

## 14. 完成定义

单个批次只有同时满足以下条件才能标记 `CLOSED`：

- 范围内代码、合同、迁移和文档已完成。
- 全部必需测试和真实运行证据通过。
- 新旧差异均已解释并批准。
- 切流与观察期通过，或已安全回滚。
- ReleaseIdentity、命令、退出码、Hash和证据路径可复现。
- 当前能力矩阵和相关决策记录已同步。
- 未引入新的重复状态、未登记变量或跨层旁路。
- 用户既有无关改动保持完整。

项目级重构完成还要求所有获准批次关闭、核心链路有当前 `LIVE_E2E` 证据、旧实现清理门禁通过，并由唯一实施顺序文档明确宣布收口。
