# 用现有项目练习，而不是另背一套术语

对应 [差距清单](review.md)，从图册的理想模型开始，先自己回答，再让 AI 检查。下面是学习顺序，不是新的 RF 开发路线。每次 45–90 分钟；没有必要全部一次做完。

## 练习一：领域语言与单位（M01–M03）

先不用 AI：画 LoanApplication→ApprovedTerms→CoreLoan 的字段流。写清本金、报价年率、批准年率、核心每期率、每期频率、还款方式和期数。回答“4.35%、0.3625%、36 期分别是什么”。

交付一张字段对照表和两个例子：同一金额/期限、等额本息与等额本金，提交核心请求必须不同；36 期回读不能静默变成 24 期。你不需要手写金融计算器：Fineract 决定正式计划，你负责映射和显示含义。

验收：不看代码能解释每个数值的单位；再打开代码定位单位丢失点。能说清为什么“字段叫 interestRate”不够明确。

AI 提示词：

> 只审查 LoanApply、LoanWorkflowService、FineractLoanPort、CustomerController、LoanDetail 和相关 OpenAPI。先列字段来源、单位、转换责任，再给两个能证伪当前实现的输入。不修改代码，不以 DTO 字段存在或本地测试 PASS 证明业务正确。区分核心请求错误、响应映射错误与 UI 标签错误。

## 练习二：事务边界与故障窗口（M04、M05、M07、M08、M11）

自己补全 [转账时序](transfer-sequence.puml)：每次 DB commit 画横线，每次网络请求画虚线边界；在核心收到、核心提交、响应到达、本地回读、本地落库之间标记进程退出。

对每个退出点写三件事：本地已知什么、核心可能做了什么、下一次允许做什么。必须出现“结果未知”，不能把所有异常都画成 FAILED。

再把 EOD 检查点与贷款还款放在旁边：同样的失败点为什么没有同样的恢复能力？不要用“核心支持幂等”一句话跳过作用范围、请求指纹、持久化时长和回读依据。

验收：给定“核心成功但响应丢失”，你能解释为什么重发 POST 与回读不是同一个动作；给定同键不同日期，你能设计零副作用的 409 测试。

AI 提示词：

> 将这个流程分成已提交本地状态、远程可能状态、当前可观察证据、允许下一动作四列。只使用代码中现有事务边界。标记 Spring 自调用和远程成功到检查点之间的窗口。不要补万能重试；给一个最小隔离故障注入方案，不在留存演示环境推进日期。

## 练习三：模块化不等于搬文件（M09、M10、M16）

先选择一个变更：“转账筛选增加收款人名称，数据库别名调整”。预测哪些文件应改、哪些不应改。然后沿 TransferController→TransferRepository 追踪实际传播路径。

手工写一个本业务 TransferFilter 的草图，只含现有筛选项；明确 Controller 解析 HTTP、Service 决定业务、Repository 决定 SQL。保留允许的只读跨表投影，不把它错误地改成多次远程查询。

验收：能解释为什么 EodCoordinator 依赖多个领域是合理的，Controller 把 WHERE 交给 Repository 却仍耦合；不以接口数量作为模块化评分。

AI 提示词：

> 对这个纵切面给出责任表与变更传播图。以业务所有权而非目录名判断耦合。列最小可删除复杂度，不建立通用 Repository、工厂或备用路径。先给等行为重构方案及一个验收反例，等我理解后再实现。

## 练习四：测试 Oracle 与真实完成度（M06、M14、M15）

写出“核心→总账对账”的双方来源、主键、金额/借贷方向、覆盖日期、允许差异。设计一个本地投影正确但核心日记账不一致的输入。问：现有测试会失败吗？若不会，它证明的到底是什么？

对提前还款按钮写业务 E2E：点击→输入金额→真实请求→权威结果→余额/计划变化，而不是只查按钮存在。对发布页分清“无发布记录”“验证失败”“当前身份 GO”，不自己编辑 JSON 得到 GO。

验收：能清楚区分 STATIC、CONTRACT、INTEGRATION、LIVE_E2E 与发布证据；自己写三个“假绿灯”例子。

AI 提示词：

> 先写测试 Oracle 和独立事实来源，再列测试步骤。每个 PASS 写清只能证明什么。不能用待测实现自己的本地投影验证它自己，也不能把离线模型注入称为真实 BYOK LIVE。指出未覆盖的业务差异，而非只报告测试数量。

## 练习五：识别 Agent 的闭环和边界（M13）

在图册 Agent 页标出：目标、模型计划、当前观察、动作、确定性判定、失败停止、状态持久化。区分模型参与规划和控制器执行协议；区分银行 adapter 与通用浏览器动作。

用目标“查询转账记录”作为反例：如果模型额外生成转账金额/收款人，系统是否应据此资金写入？答案与“是否取消逐次人工审批”无关。把业务输入标记为用户明确给出还是模型推导，不要把推导称为用户确认。

验收：你能演示当前产品是受约束的真实测试 Agent；同时不宣称任意网站零配置、自主修复或完整发布能力。遇到失败能指出缺的是观察、动作、断言还是协议状态。

AI 提示词：

> 对当前生产入口画观察—规划—动作—核验链。按具体代码区分模型决策、确定性编排和真实浏览器执行，不以使用 LangGraph 或调用模型作为充分证明。保持无逐次人工批准；对模型新增的资金参数给出基于用户意图的最小拒绝/缺项合同，不添加自动重试。

## 每轮 AI 编程的四句话模板

1. 这次业务目标是……，角色是……，外部可观察结果是……。
2. 不变量是……，权威来源是……，本次允许改变的接口是……。
3. 先给理想→实际的最短调用链和一个反例；在授权范围内修复，不扩展无关模块。
4. 交付改动、对应验收和仍未知的失败窗口；把旧文档与新事实的冲突明确标记。

避免只给“继续”“完成下一批”而没有重新说明这轮验收对象。可以继续自主推进，但每个阶段至少由你亲自解释一条业务链、一个反例、一条失败恢复规则；这三项比再加一层设计模式更能提高熟练度。
