# BANK-0303 execution report

Status: BLOCKED

Added the Fineract account-transfer adapter and a controlled processor. It sends
the stable channel idempotency key in both candidate header spellings, maps the
Fineract account-transfer payload, persists the returned core reference, and
emits a second status event only after the core response succeeds. The processor
is an internal route and is not exposed by the customer web surface; it must be
invoked only by a protected worker in the later operations deployment.

The local Fineract read probe passes and a direct curl against the same core
endpoint accepts the payload, but the Java HTTP adapter receives a 400 from the
running Fineract build claiming the six account-transfer fields are absent even
when the wire JSON and query parameters contain them. No channel transfer moved
to POSTED and no adapter-triggered core transaction was accepted. This requires
wire-level investigation before money E2E can proceed; it must not be marked
DONE by assumption.

Two temporary direct-core demo transfers created while isolating this mismatch
were both undone through the documented Fineract API (`command=undo`) and now
report `reversed=true`. The local demo product, clients, and savings accounts
remain as sandbox fixtures; no core database write was used.
